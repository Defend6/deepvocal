# 任务监控、队列维护与恢复

日期：2026-11-04。适用于本地测试身份、私有研究仓库与当前功能分支。迁移head为 `0007_worker_presence`。

## 心跳与诊断

worker启动后在PostgreSQL记录心跳，每5秒更新，写入最多等待4秒；独立异步任务使长任务执行期间仍能更新。正常关闭记录stopped；崩溃依靠30秒过期阈值识别。heartbeat是进程/事件循环近期有响应的证据，不证明模型、对象存储、算法效果或整个业务链路可用。当前任务没有因此延长租约，租约/版本/worker token的原有校验保持生效。

记录phase、活动任务ID、最后成功工作进展时间和脱敏故障码；不记录身份字符串、模型Key、音频、提示词或响应正文。DB暂时失败会延迟心跳写入，worker主循环遇到数据库错误后等待2秒继续恢复；Redis失败使用PostgreSQL扫描恢复并标degraded。待确认消息回收保存XAUTOCLAIM扫描游标，扫描一轮结束回到0-0，避免总从头扫描。

`GET /v1/operations/diagnostics` 必须通过本地身份依赖；所有任务统计、费用异常和最多10条需关注任务都以当前owner过滤，不接受客户端owner。全局只提供“是否有正常worker近期心跳”的服务信号，不返回worker标识、其他用户任务、活动job或账户总预算。

前端「任务运行诊断」每15秒刷新，并提供手动刷新；切身份重建组件、取消旧请求。展示各状态总数、活跃重试数、最久排队时间与待核账数。提示规则：无正常近期心跳、租约过期、排队超过60秒、过去24小时有失败任务、账本异常或10分钟未结占用。失败任务展示脱敏错误码和本人的任务编号。

## 本地操作CLI

在 `D:\deepvocal` 运行：

```powershell
.venv\Scripts\python.exe -m app.operations.cli status
.venv\Scripts\python.exe -m app.operations.cli recover
.venv\Scripts\python.exe -m app.operations.cli maintain --stream jobs
.venv\Scripts\python.exe -m app.operations.cli maintain --stream dead
```

status只读，输出全账户worker存活/过期/degraded/卡顿计数、可恢复/到期任务、未发布outbox、账本待核对数、队列长度、消费组pending/lag。15分钟无工作进展视为卡顿信号。Redis不可用输出脱敏原因并exit1，数据库不可用同样受控退出；不输出连接URL或异常详情。它是拥有本机数据库权限的运维入口，不是给普通用户的HTTP接口。容器中可用 `docker exec deepvocal-worker-1 python -m app.operations.cli status`。

recover默认只预览。显式 `--apply --batch 100` 时：对达到最大次数的过期RUNNING任务按原状态机改FAILED并写死信outbox；对到期QUEUED或有剩余次数的过期RUNNING任务补一条缺少的待发布通知。锁job且SKIP LOCKED，每批最多500。重复执行时已有未发布通知不重复创建；通知已发后再执行可能产生重复，仍依靠worker的claim与幂等保护。工具不直接执行模型/算法、不重置attempt，不重新运行终态任务。worker本身已扫描数据库恢复，CLI用于排查与显式唤醒。

## 历史消息保留

maintain默认只预览；jobs保留7天、dead保留30天，可用 `--retention-days` 显式调整为1～3650天。每次只扫描一批，默认100、最多500；只检查比数据库时间计算的截止点更旧的Stream ID。`next_cursor` 可传给下一批 `--after-id`，`batch_full`表示可能还有后续批次。保护的旧条目应在下一轮从0-0重扫，不能永久跳过。

只有显式 `--apply` 才删除Redis中的候选消息。有效job通知必须匹配已发布outbox事件和owner、job ID、事件类型，并且任务处于SUCCEEDED/FAILED/CANCELLED；任务更新时间和通知发布时间也须早于保留期。查询持有job/outbox共享锁，删除期间阻止改变判断依据。无法匹配的通知保留供人工检查。已知INVALID_NOTIFICATION死信可按保留期清除。

Redis Lua原子检查每个现有消费组：必须已经读过该消息，且该消息在所有组的PEL中均不存在，才XDEL。jobs流没有消费组时保留；dead默认没有消费组可清理，但一旦有组同样保护未读/待确认项。**不用MAXLEN裁剪，不删pending、不跳过落后的消费组。** 组长期不消费会阻止清理，应先人工调查，不自动删除组。新建消费组从历史重新回放无法恢复已经清理的通知，历史真值仍在PostgreSQL。

操作仅清除Redis通知；不删除PostgreSQL任务、outbox、幂等键、checkpoint、报告、账本或资产。没有自动清理调度，本轮未对业务队列执行实际清理；真实删改测试使用独立数据库/Redis DB15及随机测试流。preview与apply之间状态可能变化，apply会重新判断，不能把预览当删除承诺。

## 故障定位顺序

1. 页面连接失败，先查API `/ready`、Compose服务和数据库迁移；ready不检查worker或模型。
2. 排队不动，查CLI status：无live worker则启动worker；QUEUE_UNAVAILABLE则检查Redis；outbox_pending表示通知尚未发布或正在发布，并非一出现就必然故障。
3. 租约过期，先等worker扫描恢复；必要时recover预览，再按情况显式apply。不手工清空attempt、不修改worker token。
4. MODEL_ACCOUNTING_REVIEW转第40章核账；不自动释放不明费用。
5. 消息长期保留，先预览并调查未确认/未读组与对应任务，不能直接XTRIM或删除整个流。

## 验收与保留差距

PostgreSQL/Redis回归覆盖心跳跨长任务、停止标记、本人接口隔离与未登录拒绝、队列故障数据库兜底、恢复预览/幂等、不重试终态、多消费组PEL/未读/活跃任务保护、无消费组保护、死信保留/分页游标/输入边界，以及回收扫描游标。桌面/手机E2E使用显式合成失败任务验证异常展示和切身份清除，不冒充真实用户失败。

本轮本地完整后端60项通过，无跳过；新增运维回归7项包含在内。Ruff、前端生产构建通过，桌面/手机E2E共2项通过。文档设计检查91项通过；可移植模式88项通过、明确跳过3项本地私有来源检查。CLI status与三个默认预览命令已在本机服务执行；实际维护写操作只在隔离测试执行。两项既有上游弃用提示仍存在，不影响当前测试。

现有本地诊断和CLI没有Prometheus时序存储、主动消息通知、24小时无人值守监控、审计留存平台或容量自动扩展；worker历史心跳记录及PostgreSQL outbox仍需后续保留政策，未自动删除。数据库与Redis间无分布式事务：恢复可能重复通知，清理中断会留下尚未清理的条目，重跑重新判断。尚未实现OIDC、上传完成校验、真实模型联调或歌声生成，不改变之前已确认范围。
